# Inception

## Description

Inception is a system administration project. The goal is to build a small but
complete web infrastructure from scratch, running entirely inside Docker
containers orchestrated with Docker Compose.

The stack serves a WordPress website over HTTPS and is made of three services,
each isolated in its own container and each built from a hand-written
Dockerfile — no ready-made image is pulled from Docker Hub:

| Service | Role | Base image |
|---|---|---|
| **nginx** | TLS termination and web front end, the only entry point (port 443) | `debian:bookworm-slim` |
| **wordpress** | WordPress + php-fpm, listening on port 9000 (FastCGI) | `debian:bookworm-slim` |
| **mariadb** | Database server, listening on port 3306 | `debian:bookworm-slim` |

The three containers communicate over a private Docker bridge network. Only
nginx publishes a port to the host; MariaDB and php-fpm are unreachable from
outside the Docker network. Persistent data lives in two volumes bound to
directories on the host machine.

## Project description

### Use of Docker

Each service runs in its own container with a single main process running as
PID 1 in the foreground. No daemon is detached, no supervisor and no infinite
loop such as `tail -f` is used to keep a container alive: when the main process
stops, the container stops, which is the intended behaviour.

Images are built from `debian:bookworm-slim`, the penultimate stable release of
Debian, as required by the subject. All packages come from the official Debian
repositories, except WP-CLI, which is downloaded from the official WP-CLI
distribution and used to install and configure WordPress.

Each service follows the same structure:

```
requirements/<service>/
├── Dockerfile
├── conf/            # configuration files copied into the image
└── tools/           # entrypoint script
```

Each entrypoint validates its environment variables, performs first-run
initialisation if needed, and finally hands over to the main process with
`exec "$@"`, so that the server becomes PID 1 and receives `SIGTERM` correctly
on `docker stop`.

### Main design choices

**Idempotent entrypoints.** Every entrypoint distinguishes a first run from a
restart. MariaDB checks for `/var/lib/mysql/mysql`, WordPress checks for
`wp-config.php`. On a restart, initialisation is skipped and existing data is
never overwritten.

**Database initialisation through `--bootstrap`.** The MariaDB entrypoint
creates the data directory with `mariadb-install-db --skip-test-db`, then feeds
an SQL script to `mariadbd --bootstrap`. Because bootstrap mode implies
`--skip-grant-tables`, the script starts with `FLUSH PRIVILEGES`, which loads
the freshly created grant tables into memory and makes `ALTER USER`,
`CREATE USER` and `GRANT` legal again.

**Least privilege in the database.** The application account is created as
`user@'%'` (containers connect from arbitrary IPs on the bridge network) and is
granted privileges on the WordPress database only. `root` exists solely as
`root@'localhost'` and is never reachable over the network. The test database
is not created.

**php-fpm over TCP.** The Debian package listens on a Unix socket by default,
which cannot be reached from another container. A custom `www.conf` makes the
pool listen on `0.0.0.0:9000` instead.

**Startup ordering.** MariaDB defines a health check that runs a real query with
the application account. WordPress declares `depends_on: service_healthy` and,
in addition, waits for the database in its own entrypoint, so that the container
is also correct after an unsynchronised restart.

**Logs on stdout/stderr.** Distribution defaults write to files under
`/var/log`, which are invisible to `docker logs`. nginx and php-fpm are
configured to log to the standard streams instead.

**TLS.** nginx accepts TLSv1.2 and TLSv1.3 only. The self-signed certificate is
generated by the entrypoint at container start rather than baked into the image,
so that no private key is ever stored in an image layer.

### Virtual Machines vs Docker

A virtual machine emulates a complete machine: it runs its own kernel on top of
a hypervisor, boots an entire operating system, and reserves CPU and memory
upfront. Isolation is very strong, but each VM costs gigabytes of disk and tens
of seconds to boot.

A container shares the kernel of the host and isolates processes using kernel
features (namespaces for visibility, cgroups for resource limits). What is
shipped is only the file system and the process definition, so an image is
measured in megabytes and a container starts in milliseconds.

The trade-off is isolation: a container escape targets the shared kernel, while
a VM has a much smaller attack surface. For this project, containers are the
right tool — the services are Linux services, they must start quickly, and the
whole infrastructure is described by a text file that can be rebuilt identically
on any machine.

### Secrets vs Environment Variables

Environment variables are the simplest way to inject configuration. They are
declared in a `.env` file, excluded from Git, and passed to containers with
`env_file`. Their weakness is exposure: any process in the container can read
`/proc/self/environ`, `docker inspect` displays them in clear text, and a
careless error message can print them to the logs.

Docker secrets are files mounted into the container at `/run/secrets/<name>`.
They never appear in `docker inspect`, they are not inherited by child
processes, and each service only gets the secrets it asks for. With Docker
Swarm they live in an in-memory tmpfs; with plain Compose, as here, they are a
read-only bind mount of the file on the host.

This project uses both. Non-sensitive settings (user names, database name,
domain) stay in `.env`. All passwords are Compose secrets stored in `secrets/`:
the entrypoints read them from `/run/secrets/` at startup, and the MariaDB
health check reads `/run/secrets/db_password` itself, because it runs in a new
shell that does not see the entrypoint's variables. nginx gets no secret at all.

### Docker Network vs Host Network

With the default `host` network mode, a container shares the network stack of
the host directly. There is no isolation and no address translation: every
listening port is immediately exposed on the machine, and two containers cannot
listen on the same port.

A user-defined bridge network, as used here, gives the containers a private
subnet of their own. Docker provides an embedded DNS server so that containers
reach each other by service name — WordPress connects to `mariadb:3306` without
knowing any IP address — and nothing is reachable from the host unless it is
explicitly published.

This is exactly what the subject requires: only nginx publishes `443:443`,
while MariaDB and php-fpm stay private. Using the host network would expose
port 3306 of the database to the whole machine, and defeat the isolation the
project is about.

### Docker Volumes vs Bind Mounts

A named volume is a storage area fully managed by Docker, stored under
`/var/lib/docker/volumes`. It is portable, easy to back up with Docker tooling,
and does not depend on the layout of the host file system — but its content is
not directly visible from the host.

A bind mount maps an existing host directory into the container. The files stay
where the administrator can see them, which makes inspection and backup trivial,
at the cost of depending on the host path and its permissions.

This project uses named volumes declared with `driver_opts` (`type: none`,
`o: bind`), which are volumes backed by a host directory — a combination of both
approaches. The subject requires the data to be stored under the user's home
directory, so both volumes point into `$HOME/data`:

```yaml
volumes:
  db_data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: ${DATA_PATH}/mariadb
```

One practical consequence is worth knowing: `docker compose down -v` removes the
volume definitions but never deletes the host directories. Resetting the project
completely therefore requires `make fclean`.

## Instructions

### Requirements

- Docker and Docker Compose v2
- GNU Make
- `sudo` access, once, to edit `/etc/hosts`

### Setup

**1. Configure the environment file.** Copy the example and fill in every value:

```bash
cp srcs/.env.example srcs/.env
```

| Variable | Description |
|---|---|
| `MARIADB_DATABASE` | name of the WordPress database |
| `MARIADB_USER` | application account used by WordPress |
| `MARIADB_HOST` | database host name, i.e. the service name `mariadb` |
| `WP_URL` | site URL, without the scheme |
| `WP_TITLE` | site title |
| `WP_ADMIN_USER` / `WP_ADMIN_EMAIL` | administrator account — the login must not contain `admin` |
| `WP_USER` / `WP_USER_EMAIL` | second, non-administrator account |
| `DOMAIN_NAME` | domain used for the TLS certificate |

`WP_URL`, `DOMAIN_NAME`, the `server_name` in `srcs/requirements/nginx/conf/nginx.conf`
and the `/etc/hosts` entry below must all match.

No password goes in `.env`.

**2. Create the secrets.** Passwords are stored in a `secrets/` folder at the
root of the repository, which is ignored by Git:

```
secrets/
├── db_root_password.txt   # MariaDB root password
├── db_password.txt        # MariaDB password of MARIADB_USER
└── credentials.txt        # WordPress passwords
```

The two `db_*` files contain only the password. `credentials.txt` contains one
`KEY=value` per line:

```
WP_ADMIN_PASSWORD=...
WP_USER_PASSWORD=...
```

See [DEV_DOC.md](DEV_DOC.md) for more details.

**3. Resolve the domain locally.** The domain does not exist in the public DNS,
so it has to be mapped to the loopback address on the machine running the stack:

```bash
sudo sh -c 'echo "127.0.0.1 dufama.42.fr" >> /etc/hosts'
```

**4. Start the stack.**

```bash
make
```

The project is meant to be driven through `make`, which exports `DATA_PATH` and
creates the data directories before starting Compose. Running
`docker compose` directly, without that variable, will fail to mount the volumes.

### Usage

```bash
make          # build the images and start the stack in the background
make logs     # follow the logs of the three services
make ps       # show the state of the containers
make down     # stop and remove the containers, keep the data
make re       # restart the stack
make fclean   # remove containers, images, volumes and the data directories
```

Once started, the site is available at **https://dufama.42.fr** and the
administration panel at **https://dufama.42.fr/wp-admin**.

The browser will warn that the connection is not private: the certificate is
self-signed, so no certificate authority vouches for it. The connection is
encrypted nonetheless. Accept the warning to reach the site.

### Data

Persistent data is stored on the host, under `$HOME/data`:

```
~/data/mariadb     # database files
~/data/wordpress   # WordPress core, themes, plugins and uploads
```

`make down` followed by `make` preserves everything, including published posts.
Only `make fclean` erases the data.
